## Profile

Performance test engineer, eight years, mostly banking and telecom. The work divides into three
parts that people usually confuse: building a workload model that resembles reality, running it
against an environment whose relationship to production is documented rather than assumed, and
then finding out where the time actually goes. The third part is the one that requires the most
argument, because the first answer from a load test is always a number and the useful answer is
always a cause.

## Work Experience

### Senior Performance Engineer | VPBank, Ha Noi | Jan 2022 - Present
- Performance testing for the retail digital channel: mobile banking, internet banking, the
  API gateway in front of them, and the two core-facing adapters.
- Rebuilt the workload model from production traffic rather than from a business estimate.
  Nine transaction types weighted by observed volume, with a separate peak profile for the two
  hours after salary day and a third profile for the Tet period. The previous model had a flat
  transaction mix and consistently understated the load on the balance-enquiry path by around
  4x.
- The 2023 Tet readiness test is the piece of work I would point at: target 3,200 TPS on the
  balance and transfer paths, sustained for four hours. First run degraded past 1,900 TPS with
  connection pool exhaustion on an adapter that nobody owned. Configuration fix plus a
  connection-reuse change got us to 3,600 TPS with p95 at 420ms, and the actual Tet peak came
  in around 2,900 TPS with no incident.
- Run the soak tests, which is where the memory leaks are. Two in three years: a leaking
  cache entry in the notification service that took 26 hours to become visible, and an
  unbounded retry queue that only appeared under a partial dependency failure.
- Own the performance NFRs. I write them with the product owner before development, in the
  form of a percentile target for a named transaction at a named load, because "should be
  fast" is not testable and I have stopped accepting it.
- Set up continuous performance smoke tests in k6 in the CI pipeline: 12 critical endpoints,
  three minutes, comparing p95 against the last release with a 15% regression threshold. It
  has caught six regressions before they reached the release branch, including an N+1 query
  that would have been invisible until production volume.
- Capacity planning input for the annual infrastructure budget: measured throughput per node,
  headroom analysis, and the growth projection. This started as a favour and is now half of
